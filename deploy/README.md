# Доступ через Linux-сервер

Linux-шлюз принимает HTTPS и передаёт запросы через обратный SSH-туннель. Сам пульт Node.js, OBS Studio, FFmpeg DirectShow, Spotify и загруженные файлы продолжают работать на компьютере с Windows. Для локального Wi‑Fi текущий режим работает без шлюза.

```text
Телефон или браузер
  → HTTPS, пароль шлюза и код пульта
  → Caddy на Linux
  → 127.0.0.1:18787 на Linux
  → обратный SSH-туннель с Windows
  → 127.0.0.1:8787 на Windows
  → OBS WebSocket 4455 и локальные интеграции
```

## Linux

1. Укажи DNS для поддомена, например `obs.example.com`. Нужен Linux с SSH и доступными для Caddy TCP 80/443. Если на сервере уже запущен Caddy, добавь сайт из [Caddyfile](./Caddyfile) в существующую конфигурацию и передай те же переменные окружения.
2. Используй отдельного SSH-пользователя, например `obs-tunnel`, и ключ. Ограничение для него в `sshd_config` можно задать в конце файла. Проверь синтаксис `sshd -t` перед применением.

   ```text
   Match User obs-tunnel
       AllowTcpForwarding remote
       GatewayPorts no
       PermitListen 127.0.0.1:18787
       PermitTTY no
       MaxSessions 0
   ```

3. В папке `deploy` создай локальный `.env` по примеру. Получи bcrypt-хеш для пароля, который браузер будет запрашивать перед входом. Команда спрашивает пароль интерактивно.

   ```bash
   cp .env.example .env
   docker run --rm -it caddy:2.11.9-alpine caddy hash-password
   ```

   Вставь хеш в `OBS_REMOTE_PASSWORD_HASH` в одинарных кавычках, чтобы Compose не интерпретировал `$` внутри хеша. Заполни `OBS_REMOTE_DOMAIN` и `OBS_REMOTE_USER`. Пример содержит условный домен и заглушку. Не добавляй рабочий `.env` в Git.

   ```bash
   docker compose config --quiet
   docker compose up -d
   docker compose ps
   ```

   Контейнер использует сеть хоста Linux, чтобы подключаться к loopback-порту SSH-туннеля. Порт 18787 слушает только loopback. Порты 4455 и 8787 на Windows пробрасывать наружу не нужно.

## Windows

1. Открой OBS. Запусти пульт с переменной окружения, равной точному HTTPS-адресу шлюза. Значение вводится в PowerShell без завершающего слэша.

   ```powershell
   $env:OBS_REMOTE_PUBLIC_ORIGIN = 'https://obs.example.com'
   & '.\Пульт OBS\start-remote.cmd'
   ```

2. В отдельном окне PowerShell запусти [start-tunnel.ps1](./start-tunnel.ps1) из корня репозитория.

   ```powershell
   & '.\deploy\start-tunnel.ps1' -Gateway 'obs-tunnel@obs.example.com'
   ```

   Туннель работает, пока запущен SSH. При первом подключении сравни отпечаток SSH-ключа сервера с ожидаемым. При нестандартных портах согласуй `-TunnelPort` и `-LocalPort` с переменными в `.env`.

3. Открой домен шлюза, авторизуйся и введи код с [локальной страницы подключения](http://127.0.0.1:8787/pair) на компьютере с OBS. После перезапуска пульта используй свежий код. Публичный шлюз не выдаёт QR или код. Запросы из браузера передают код в `X-OBS-Code`, а команды через шлюз требуют совпадающий HTTPS Origin.

## Проверить

- Без авторизации домен должен показать запрос пароля. После авторизации должны отображаться пульт и экран ввода кода. `/pair` и `/api/pair` на домене должны быть недоступны.
- После ввода кода должен появляться кадр OBS. В браузере проверь сетевой запрос `/api/video`, он передаёт fMP4 по мере поступления.
- Если шлюз отвечает 502, проверь со стороны Linux, что `curl -fsS -o /dev/null http://127.0.0.1:18787/` устанавливает соединение и получает страницу.
- Если OBS выключен, pairing и интерфейс остаются доступны, а чтение состояния OBS временно возвращает 503. Запускать реальный эфир для проверки не требуется.
